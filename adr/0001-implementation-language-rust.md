# ADR-0001: 구현 언어로 Rust를 채택한다

- **상태**: 채택됨
- **일자**: 2026-08-06
- **관련**: 프로젝트 헌장 — 단계 0(기반), 아키텍처 제약(외부 의존성 없음, 에어갭 설치, 단일 노드 우선, 운영 부담 최소화)

## 맥락

헌장은 이 제품을 셀프호스팅 서버로 규정한다. 여기서 두 가지 요구가 나왔다.

1. **기능이 많아도 런타임이 무겁지 않을 것.** 설치 주체가 고객사이고 상당수는
   VM 한 대에서 돌린다. 런타임 풋프린트가 곧 도입 장벽이다.
2. **아키텍처 제약이 없을 것.** x86_64에 묶이면 ARM 기반 서버·사내 장비·
   개발자 워크스테이션에 설치할 수 없다.

두 요구는 서로를 강화한다. GC 런타임이나 인터프리터에 의존하면 메모리 풋프린트가
커지고, 배포 산출물이 런타임 설치를 전제하게 되어 에어갭 설치도 어려워진다.

## 결정

**구현 언어로 Rust를 채택한다.** 서버 측 구성 요소(API, git 서버, 러너, 웹훅, CLI)는
Rust로 작성한다.

근거는 헌장의 제약과 직접 대응한다.

| 헌장 제약 | Rust가 대응하는 방식 |
| --- | --- |
| 외부 의존성 없음 | 런타임(JVM, Node, Ruby) 설치가 필요 없는 네이티브 바이너리 |
| 에어갭 설치 | 정적 링크 단일 바이너리로 배포 가능, 설치 시 패키지 다운로드 불필요 |
| 단일 노드 우선 | GC 없는 메모리 모델로 유휴 풋프린트가 작고 예측 가능 |
| 운영 부담 최소화 | 구성 요소를 하나의 바이너리로 합칠 수 있어 프로세스·포트 수 감소 |
| 보안 (CI 격리, 임의 입력 처리) | 메모리 안전성이 파싱·프로토콜 처리 계층의 취약점 부류를 제거 |

## 검증한 사실 — 아키텍처 지원 범위

Rust 공식 플랫폼 지원표에서 확인한 결과다. "제약 없음"의 실제 경계는 아래와 같다.

| 타깃 | 등급 |
| --- | --- |
| `x86_64-unknown-linux-gnu` | Tier 1 (host tools) |
| `aarch64-unknown-linux-gnu` | Tier 1 (host tools) |
| `aarch64-unknown-linux-musl` | Tier 2 (host tools) |
| `x86_64-unknown-linux-musl` | Tier 2 (**without** host tools) |
| `armv7-unknown-linux-gnueabihf` | Tier 2 (host tools) |
| `riscv64gc-unknown-linux-gnu` | Tier 2 (host tools) |
| `powerpc64le-unknown-linux-gnu` | Tier 2 (host tools) |
| `s390x-unknown-linux-gnu` | Tier 2 (host tools) |
| `loongarch64-unknown-linux-gnu` | Tier 2 (host tools) |

등급의 의미:

- **Tier 1** — 공식 바이너리 배포본이 빌드되고, 모든 변경마다 자동 테스트가 돈다.
- **Tier 2** — 표준 라이브러리 빌드는 보장되지만 **자동 테스트는 보장되지 않는다.**

주목할 점: 에어갭 단일 바이너리에 가장 잘 맞는 **musl 정적 링크 타깃이 Tier 1이 아니다.**
`x86_64-unknown-linux-musl`은 host tools도 없다. 크로스 컴파일 대상으로는 문제없지만,
"Tier 1이니까 안전하다"는 가정은 성립하지 않는다.

## 파생 요구사항

### 지원 등급 정책

Rust의 등급 체계를 그대로 제품 지원 정책으로 가져온다.

| 등급 | 대상 | 약속 |
| --- | --- | --- |
| **보장** | `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu` | 릴리스마다 빌드 + 전체 테스트 통과. 회귀는 릴리스 차단 사유 |
| **최선 노력** | 위 둘의 musl 변형 | 릴리스마다 빌드 + 스모크 테스트. 결함은 수정하되 릴리스를 막지 않음 |
| **커뮤니티** | armv7, riscv64gc, ppc64le, s390x, loongarch64 | 빌드만 확인. 테스트·수정은 요청 기반 |

이 정책의 핵심은 **아키텍처를 배제하지 않되, 지키지 못할 약속을 하지 않는 것**이다.
"제약 없음"은 "어디서든 빌드된다"로 구현하고, "어디서든 검증했다"고 주장하지 않는다.

### CI 요구사항

- 보장 등급 두 타깃에 대해 **네이티브 실행 테스트**를 돌린다. 크로스 빌드만으로는
  Tier 2 타깃의 테스트 미보장 문제를 덮을 수 없다.
- 커뮤니티 등급은 크로스 컴파일 빌드 검증까지만 한다.
- 이 요구사항은 `github-clone-actions-runner`가 스스로를 검증해야 하는
  단계 4에서 순환 의존이 생긴다. 그때까지는 외부 CI를 쓴다.

### 의존성 선택 규칙

**아키텍처 이식성을 실제로 제약하는 것은 Rust가 아니라 크레이트 의존성이다.**
C 라이브러리에 링크하는 크레이트는 타깃마다 크로스 툴체인을 요구하고,
손으로 쓴 어셈블리를 포함하는 크레이트는 지원 아키텍처가 제한된다.

따라서 규칙을 둔다.

1. 순수 Rust 구현이 있으면 그것을 우선한다.
2. C 의존성을 도입하려면 그 크레이트가 보장 등급 두 타깃에서
   크로스 빌드되는지 확인하고, 결과를 이 ADR의 후속 문서에 기록한다.
3. 벤더링(bundled) 빌드가 가능한지 확인한다 — 시스템 라이브러리 설치를 요구하면
   에어갭 설치 제약에 걸린다.

아래는 **검증 대상 후보**다. 아직 확인하지 않았으므로 결정이 아니다.
단계 0에서 각각 실제 빌드로 확인한 뒤 별도 ADR로 확정한다.

| 영역 | 확인할 것 |
| --- | --- |
| git 객체 접근 | 순수 Rust 구현과 libgit2 바인딩 중 무엇이 이식성·성숙도 균형에서 나은가. 헌장의 "초기에는 `git` 실행 파일을 감싼다" 전략과의 정합성 |
| TLS | 순수 Rust 백엔드로 보장 등급 타깃을 모두 덮는가. 어셈블리 기반 암호 라이브러리의 아키텍처 지원 범위 |
| 데이터베이스 | 내장 DB의 벤더링 빌드가 크로스 컴파일되는가. 외부 DB 클라이언트에 순수 Rust 선택지가 있는가 |
| 전문 검색 | 순수 Rust 검색 엔진이 코드 검색 요구를 감당하는가 |
| 압축 | git pack·아티팩트 압축에 쓸 구현의 C 의존 여부 |

### 경량성 목표 (잠정)

"덜 무겁게"를 측정 가능한 형태로 옮긴다. 아래 수치는 **잠정 목표**이며,
단계 1에서 실측한 뒤 확정한다.

- 사용자 20명 규모 설치에서 유휴 상태 RSS **512MB 이하**
- 최소 권장 사양 **2 vCPU / 4GB RAM / 20GB 디스크**
- 코어 배포 바이너리 **100MB 이하**
- 콜드 스타트에서 요청 수락까지 **5초 이내**

이 수치는 릴리스마다 측정해 회귀를 감시한다. 측정하지 않는 목표는 목표가 아니다.

### 기능 증가에 대한 대응

기능 전부를 담으면서 가볍기는 자동으로 얻어지지 않는다. Rust는 전제 조건일 뿐이다.
아래를 설계 요구로 둔다.

- **컴파일 타임 기능 분리** — Cargo feature로 미사용 기능을 바이너리에서 제외
- **런타임 지연 초기화** — 쓰지 않는 하위 시스템(패키지 레지스트리, 검색 색인)은
  활성화 전까지 자원을 잡지 않음
- **선택적 프로세스 분리** — 기본은 단일 바이너리, 규모가 커지면 구성 요소를
  분리 실행. 같은 코드베이스에서 두 배치 모두 지원

## 결과

**긍정**

- 런타임 설치 없는 배포로 에어갭·업그레이드 절차가 단순해진다
- 메모리 풋프린트가 예측 가능해 최소 사양 약속을 지킬 수 있다
- 보장 등급 두 아키텍처가 모두 Rust Tier 1이라 툴체인 리스크가 낮다
- CLI(`ghc`)와 서버가 같은 언어·타입 정의를 공유할 수 있다

**부정 / 감수하는 것**

- 컴파일 시간이 길다. CI 시간과 개발 반복 속도에 부담이 된다
- 웹 생태계의 기성 부품이 적어 직접 구현할 범위가 넓어진다
- 인력 확보가 상대적으로 어렵다
- 아키텍처를 늘릴수록 CI 매트릭스가 곱셈으로 커진다. 지원 등급 정책으로
  비용을 통제하는 이유다

## 미결 사항

이 ADR은 **언어만** 정한다. 아래는 후속 ADR로 다룬다.

- **웹 프런트엔드 방식** — Rust/WASM 프레임워크로 갈 것인가, 서버사이드 렌더링에
  최소한의 JavaScript를 더할 것인가. 경량성 목표에는 후자가 유리해 보이나
  대형 diff 뷰어 같은 상호작용 요구를 감당하는지 확인이 필요하다
- **웹 프레임워크·비동기 런타임 선택**
- **데이터베이스** — 내장 DB만으로 갈 것인가, 외부 DB를 기본으로 둘 것인가
- **CI 러너의 격리 방식** — 컨테이너 런타임 의존은 아키텍처별 이미지 문제를
  낳으며, 이는 Rust와 무관한 제약이다
