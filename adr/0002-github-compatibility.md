# ADR-0002: GitHub 호환성을 1급 요구사항으로 채택한다

- **상태**: 채택됨
- **일자**: 2026-08-06
- **관련**: [ADR-0001](0001-implementation-language-rust.md), 프로젝트 헌장 — 성공의 정의(대체 가능성, 도구 호환), 열린 질문

## 맥락

헌장은 두 가지를 열린 질문으로 남겨 두었다.

- CI 워크플로 문법을 GitHub Actions와 호환시킬 것인가, 자체 정의할 것인가
- API를 GitHub REST/GraphQL과 형태까지 호환시킬 것인가

두 질문의 답이 "호환한다"로 정해졌다. 이는 헌장의 성공 기준 2번(대체 가능성)과
3번(도구 호환)을 강화하는 방향이며, 제품의 핵심 가치 제안을 바꾼다.

**호환이 곧 제품의 해자다.** 사용자가 이 제품으로 옮겨오는 비용의 대부분은
기능 학습이 아니라 기존 자산의 이전이다. 워크플로 파일, CI 통합, 봇, 스크립트,
IDE 플러그인, 사내 자동화가 그대로 동작하면 이전 비용이 붕괴한다.
동작하지 않으면 기능이 아무리 많아도 옮겨올 이유가 없다.

## 결정

**GitHub과의 호환성을 1급 요구사항으로 삼는다.** 설계 판단이 갈릴 때
"더 나은 설계"보다 "GitHub과 같은 동작"을 우선한다.

단, 호환의 종류를 구분한다. 전부를 같은 강도로 맞출 수는 없다.

### 호환 등급

| 등급 | 대상 | 기준 |
| --- | --- | --- |
| **L1 — 와이어 호환** | git 프로토콜, REST API, 웹훅 페이로드, 워크플로 파일 문법, 저장소 내 설정 파일(CODEOWNERS, 이슈·PR 템플릿), 마크다운 방언 | 기존 클라이언트가 **수정 없이** 동작해야 한다. 불일치는 결함으로 취급한다 |
| **L2 — 형태 호환** | GraphQL 스키마, URL 구조, 권한 모델의 역할 이름 | 같은 개념·같은 이름을 쓴다. 세부 필드 차이는 문서화하고 허용한다 |
| **L3 — 호환 대상 아님** | 관리자 콘솔, 설치·백업·업그레이드, 라이선스, 인스턴스 설정 | GitHub.com에 대응물이 없거나 셀프호스팅 고유 영역이다. 자유롭게 설계한다 |

### 호환의 판정 기준

호환 여부를 우리 판단으로 정하지 않는다. **기존 GitHub 클라이언트를 우리 서버에
붙여 통과하는지로 판정한다.** 이것이 유일하게 의미 있는 검증이다.

- 표준 `git` 클라이언트로 clone / push / pull 왕복
- GitHub 공식 CLI를 인스턴스 호스트 지정으로 붙여 주요 명령 수행
- 공식 API 클라이언트 라이브러리로 저장소·이슈·PR 조작
- 실제 프로젝트의 워크플로 파일을 수정 없이 실행

이 적합성 시험을 CI에 넣는다. 통과하지 못하면 릴리스하지 않는다.

## 이 결정이 만드는 충돌

호환 요구는 헌장의 기존 제약과 두 군데에서 충돌한다. 숨기지 않고 기록한다.

### 충돌 1 — 에어갭 설치 vs 워크플로 액션 재사용 (심각)

워크플로 문법을 호환하면 워크플로 파일은 외부 저장소의 재사용 가능한 액션을
참조한다. 그 액션들은 GitHub.com에서 내려받는 것이 기본 동작이다.

이는 헌장의 **에어갭 설치** 제약("런타임에 외부 레지스트리를 호출하는 설계를
금지한다")을 정면으로 위반한다. 문법만 호환하고 액션 해석을 그대로 두면,
폐쇄망에서는 대부분의 실제 워크플로가 실패한다. **문법 호환은 워크플로 호환이 아니다.**

해소 방향(후속 ADR에서 확정):

- 액션 참조를 인스턴스 내부 미러로 해석하는 계층을 둔다
- 관리자가 필요한 액션을 사전에 인스턴스로 가져오는 절차를 제공한다
- 자주 쓰이는 핵심 액션에 대해 내장 구현을 제공하는 안을 검토한다
- 어떤 경우에도 **런타임에 외부로 나가지 않는 것이 기본값**이어야 한다

재배포를 수반하므로 대상 액션의 라이선스를 개별 확인해야 한다.

### 충돌 2 — 호환 vs 설계 자유도

GitHub의 API에는 오랜 기간 누적된 비일관성과 역사적 잔재가 있다.
호환을 우선하면 그것까지 재현하게 된다.

원칙을 둔다. **관측 가능한 동작은 재현하고, 내부 구조는 재현하지 않는다.**
클라이언트가 구분할 수 없는 차이는 우리 방식대로 만든다.
클라이언트가 구분할 수 있는 차이는 GitHub을 따른다.

헌장의 제외 항목("소스 코드 수준 호환 — 내부 구현을 베끼지 않는다")은
이 결정과 충돌하지 않는다. 오히려 이 원칙의 다른 표현이다.

## 파생되는 변경

### `ghc` CLI의 위치가 바뀐다

REST API를 L1 등급으로 호환하면, **GitHub 공식 CLI가 호스트 지정만으로
우리 서버에 붙는다.** `ghc`가 "gh 대체"라는 존재 이유의 상당 부분이 사라진다.

`ghc`를 유지하되 목표를 옮긴다.

- 호환 계층의 **적합성 시험 도구** — 우리 API가 공식 클라이언트와 같은 응답을 내는지
  대조하는 기준 구현
- 공식 CLI에 대응물이 없는 **셀프호스팅 고유 영역**(L3)의 조작 —
  인스턴스 설정, 백업·복구, 사용자 관리, 업그레이드
- 오프라인·최소 의존 환경용 단일 바이너리 클라이언트

즉 `ghc`는 공식 CLI를 대체하는 것이 아니라, 그것이 다루지 않는 영역을 맡는다.

### 마이그레이션이 범위로 들어온다

성공 기준 2번(기존 GitHub 조직을 가져와 계속 일할 수 있다)이 호환 요구와 결합해
구체적 기능이 된다. 저장소·이슈·PR·릴리스·워크플로 이력의 가져오기를
Tier 2 범위에 포함한다.

### 상표와 브랜드는 여전히 제외

호환은 형태와 동작의 문제이지 이름의 문제가 아니다. 헌장의 상표 사용 제외는
그대로 유지한다. API 경로나 필드 이름처럼 호환에 불가피한 문자열은 예외로 본다.

## 결과

**긍정**

- 이전 비용이 극적으로 낮아진다. 이것이 도입의 최대 장벽이었다
- 기존 도구 생태계를 그대로 쓴다. 우리가 만들지 않아도 되는 것이 많아진다
- 요구사항 도출이 쉬워진다. 명세의 상당 부분이 이미 공개되어 있다
- 적합성 시험이라는 객관적 완료 기준이 생긴다

**부정 / 감수하는 것**

- 설계 자유도를 잃는다. 우리가 더 낫다고 판단해도 호환을 우선한다
- 상대가 움직이는 표적이다. GitHub의 변경을 계속 따라가야 한다
- 호환 표면이 넓어 "몇 %가 호환되는가"를 항상 측정하고 공개해야 한다.
  측정하지 않으면 호환한다는 주장은 검증 불가능한 마케팅이 된다
- 에어갭 제약과의 충돌(위 충돌 1)이 실제 구현 난이도를 크게 올린다

## 미결 사항

- 액션 미러링·번들링의 구체 방식과 대상 액션의 라이선스 검토 (충돌 1 해소)
- 호환 기준으로 삼을 GitHub API 버전과, 상류 변경 추종 주기
- GraphQL 스키마를 어느 깊이까지 맞출 것인가 (L2의 구체 경계)
- 호환율 측정 방법과 공개 형식
