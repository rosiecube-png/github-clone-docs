## 왜 여기에 없는가

요구사항은 상태가 계속 바뀌고, 담당이 붙고, 구현과 연결된다.
마크다운 파일은 그 어느 것도 하지 못한다. 두 곳에 두면 반드시 어긋난다.

이 디렉터리에는 Projects가 담기 어려운 것만 남긴다.

## 항목 구성

요구사항 하나가 Project 항목 하나다. 현재 185개(FR 135 · NFR 50).

제목은 `FR-GIT-01 - Smart HTTP 전송` 형식이고, 본문에 출처·서술·수용 기준·비고가 들어간다.

## 필드

| 필드 | 값 |
| --- | --- |
| 요구사항 ID | `FR-GIT-01` 형식. 한 번 부여하면 재사용하지 않는다 |
| 종류 | `FR` / `NFR` |
| 도메인 | `FR-GIT`, `NFR-SEC` 등 38종 |
| Tier | `T1` 이것이 없으면 제품이 아니다 / `T2` 팀이 쓰려면 필요하다 / `T3` GitHub 동등성 |
| 요구사항 상태 | `초안` / `확정` / `보류` / `폐기` |
| 호환 등급 | `L1` 와이어 호환 / `L2` 형태 호환 / `L3` 호환 대상 아님 / `해당없음` |
| 담당 저장소 | 구현을 맡을 저장소. NFR은 대부분 `교차` |

`Status`(Todo / In Progress / Done)는 작업 진행용이고,
`요구사항 상태`는 요구사항 자체의 합의 수준이다. 둘은 다른 축이다.

## 작성 규칙

모든 요구사항은 아래를 갖춘다. 하나라도 없으면 초안 이전 상태다.

1. **서술** — 무엇을 만족해야 하는지. "빠를 것" 같은 서술은 금지한다.
2. **수용 기준** — 어떻게 통과를 판정하는지. 자동으로 확인할 수 있어야 한다.
3. **출처** — 헌장의 어느 항목 또는 어느 ADR에서 파생됐는지.

**측정하지 않는 요구사항은 요구사항이 아니다.** 수치를 적을 수 없으면
수치를 정할 방법이라도 적는다.

호환 등급이 `L1`인 요구사항의 수용 기준은 **기존 GitHub 클라이언트로 판정한다**
(NFR-COMPAT-02). 우리가 만든 클라이언트로 통과시킨 것은 통과가 아니다.

## 현재 상태

- 전 도메인(T1·T2·T3) 전개 완료. 헌장의 범위 전체를 덮는다.
- 상태 분포: 초안 166 · 보류 12 · 확정 7
- 다수 수치가 `잠정`이다. 단계 1 실측 후 확정하며,
  그 위에 되돌릴 수 없는 결정을 쌓지 않는다.
- `보류` 항목이 막힌 이유는 [open-questions.md](open-questions.md)에 있다.
- 세부 정확도는 도메인마다 다르다. T1이 가장 촘촘하고 T3로 갈수록 성기다.
  착수하는 도메인은 착수 전에 다시 다듬는다.
