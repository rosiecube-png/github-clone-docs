# 요구사항 체계

이 디렉터리는 프로젝트 헌장에서 파생된 검증 가능한 요구사항을 담는다.

| 문서 | 내용 |
| --- | --- |
| [fr.md](fr.md) | 기능 요구사항 (Functional Requirements) |
| [nfr.md](nfr.md) | 비기능 요구사항 (Non-Functional Requirements) |

## 헌장과의 관계

헌장은 **범위와 방향**을 정한다. 요구사항은 **검증 가능한 형태**로 그것을 옮긴다.

헌장의 "기능 요구 영역", "비기능 요구 영역" 절은 범주 목록이지 요구사항이 아니다.
그 범주들이 여기서 개별 요구사항으로 전개된다.

요구사항은 헌장과 충돌할 수 없다. 충돌하면 헌장을 먼저 고친다.

## ID 규칙

```
FR-<도메인>-<번호>     기능 요구사항   예: FR-GIT-01
NFR-<범주>-<번호>      비기능 요구사항 예: NFR-LIGHT-01
```

ID는 한 번 부여하면 재사용하지 않는다. 폐기된 요구사항은 번호를 비워 두고
상태만 `폐기`로 바꾼다. 문서 어디서든 ID로 참조한다.

## 요구사항 작성 규칙

모든 요구사항은 아래를 갖춘다. 하나라도 없으면 초안 이전 상태다.

1. **서술** — 무엇을 만족해야 하는지. "빠를 것" 같은 서술은 금지한다.
2. **수용 기준** — 어떻게 통과를 판정하는지. 자동으로 확인할 수 있어야 한다.
3. **출처** — 헌장의 어느 항목 또는 어느 ADR에서 파생됐는지.

**측정하지 않는 요구사항은 요구사항이 아니다.** 수치를 적을 수 없으면
수치를 정할 방법이라도 적는다.

## 상태

| 상태 | 뜻 |
| --- | --- |
| `초안` | 작성됐으나 검토·합의 전 |
| `확정` | 합의됨. 변경하려면 근거를 남긴다 |
| `보류` | 선행 결정을 기다리는 중 |
| `폐기` | 더 이상 유효하지 않음. ID는 재사용하지 않음 |

## 우선순위

헌장의 Tier 구분을 그대로 쓴다.

| Tier | 뜻 |
| --- | --- |
| `T1` | 이것이 없으면 제품이 아니다 |
| `T2` | 팀이 실제로 쓰려면 필요하다 |
| `T3` | GitHub 동등성 |

## 호환 등급

ADR-0002의 등급을 그대로 쓴다. 기능 요구사항에만 붙는다.

| 등급 | 뜻 |
| --- | --- |
| `L1` | 와이어 호환. 기존 클라이언트가 수정 없이 동작해야 한다 |
| `L2` | 형태 호환. 같은 개념·이름을 쓰되 세부 차이는 문서화 후 허용 |
| `L3` | 호환 대상 아님. 셀프호스팅 고유 영역 |

## 현재 진척

정직하게 적는다.

- **NFR** — 전체 범주를 덮었다. 다수 항목의 수치가 `잠정`이며 단계 1 실측 후 확정한다.
- **FR** — T1만 상세화했다. T2·T3는 도메인과 ID 접두사만 예약했고 전개하지 않았다.
  헌장의 범위를 좁힌 것이 **아니다**. T1 구현으로 도메인 모델이 드러난 뒤에
  전개하는 편이 낫다고 판단한 것이며, 단계 2 종료 시점에 T2를 전개한다.
