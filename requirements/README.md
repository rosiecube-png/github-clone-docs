이 디렉터리에는 Projects가 담기 어려운 것만 남긴다.

감사에서 가장 무겁게 드러난 것은 기능 누락이 아니라 **제품 조건**이었다.
기능은 눈에 보이고 언젠가 채워지지만, "폐쇄망 고객에게 보안 패치를 줄 방법이
없다"를 기능 완성 후에 발견하면 아키텍처를 되돌려야 한다.

`NFR-LIFECYCLE-01`(보안 패치 전달)은 **CON-01(에어갭)과 부딪히는 두 번째
지점**이다. 액션 미러링(Q-01)과 같은 종류의 문제이며, 그때는 아무도
제기하지 않았다.

### 가정과 제약을 나누는 이유

**가정이 틀리면 재설계이고, 제약을 어기면 결함이다.** 섞어 두면
"검증할 대상"과 "준수할 대상"이 구분되지 않는다.

제약은 다시 출처로 나눈다. 그래야 뒤집을 수 있는지 판단할 수 있다.

- **외부 강제** — 에어갭, 고객 인프라, 상류 GitHub API 형태, Rust 지원 등급,
  제3자 라이선스, 브라우저 보안 모델. 협상 불가.
- **우리 선택** — Rust 채택, 호환 우선, 단일 노드 우선, 멀티테넌트 제외.
  ADR로 뒤집을 수 있다.

### 단계 — 왜 GitHub 마일스톤을 쓰지 않는가

마일스톤은 실재하고 `gh`도 지원하지만(`gh issue create --milestone`, REST
`repos/{owner}/{repo}/milestones`), 이 구조에는 붙지 않는다. 확인한 사실은 셋이다.

1. **마일스톤은 저장소 단위 개념이다.** 우리 항목은 초안 항목이라 저장소에
   속하지 않는다.
2. **프로젝트 필드 값으로 마일스톤을 설정하는 경로가 없다.** 필드 값이 받는 것은
   텍스트·숫자·날짜·단일선택·다중선택·반복주기뿐이다. Project의 Milestone 필드는
   연결된 이슈에서 파생되는 읽기 전용이다.
3. **단계가 저장소를 가로지른다.** 이슈로 전환하더라도 한 단계가 8개 저장소에
   걸치므로 저장소마다 같은 마일스톤을 복제해야 하고, 단계 전체를 한 화면에서
   볼 수 없다.

그래서 단일 선택 필드로 둔다. 대신 마일스톤이 주는 기한과 완료율 막대는 잃는다.
이슈로 전환하면 둘을 병용할 수 있다 — 교차 조회는 `단계` 필드, 저장소별 기한은
마일스톤.

### 단계 배정 규칙

도메인의 의존 순서로 기본 단계를 정하고, `T3` 항목은 `6 동등성`으로 미룬다.
개별 항목은 명시 지정으로 덮는다. `CON`은 특정 단계에 속하지 않으므로 `전 단계`다.

| 단계 | 계 | 성격 |
| --- | --- | --- |
| 0 기반 | 8 | 요구사항이 아니라 **검증 과제**다. 전부 `ASM`이며 착수 전에 답이 나와야 한다 |
| 1 Git 서버 | 26 | |
| 2 플랫폼 코어 | 63 | |
| 3 협업 | 44 | dogfooding 전환 지점 |
| 4 자동화 | 48 | |
| 5 배포 가능 | 66 | 제품 조건(NFR) 31개가 여기 몰려 있다 |
| 6 동등성 | 82 | `T3` 77개가 규칙에 따라 밀린 결과다 |
| 전 단계 | 13 | `CON` 11 + 상시 지켜야 하는 `NFR` 2 |

**단계 6이 82개로 가장 크다.** 이는 판단이 아니라 `T3 → 6` 규칙의 산술적 결과다.
실제로는 해당 도메인에 착수하는 시점에 앞당겨질 항목이 섞여 있다.

배정 검증에서 `T1`인데 단계 5로 밀린 항목 2개(`NFR-OPS-01` 에어갭 설치,
`NFR-OPS-03` 외부 서비스 비의존)가 나와 `전 단계`로 고쳤다.
이 둘은 나중에 만드는 기능이 아니라 첫 줄부터 지켜야 하는 조건이다.

`Status`(Todo / In Progress / Done)는 작업 진행용이고,
`요구사항 상태`는 합의 수준이다. 둘은 다른 축이다.

### 재검토 기한은 일정 추정이 아니다

가정 15개 전부에 `2026-09-30`이 들어가 있다. 이것은 "그때까지 끝난다"는
예측이 **아니라**, 그때까지 검증되거나 기한이 의도적으로 연장되지 않으면
그 위에 쌓인 것을 신뢰할 수 없다는 **강제 점검 주기**다.

만료 없는 잠정치는 영구 잠정치가 된다. `잠정`이라는 딱지는 검증이 아니라
검증 연기이며, 기한이 그것을 다시 표면으로 끌어올린다.

### 가정에는 무효화 영향이 미리 적혀 있어야 한다

가정이 깨진 뒤에 "무엇을 다시 봐야 하지"를 찾기 시작하면 늦다.
모든 ASM 항목 본문에 **무효화 시 영향**을 적는다.

가장 무거운 것은 `ASM-14`(폐쇄망 수요의 실재)다. 제품 전제 전체가
그 위에 서 있으며 아직 검증된 적이 없다. 다른 어떤 검증보다 우선한다.

## 작성 규칙

모든 요구사항은 아래를 갖춘다. 하나라도 없으면 초안 이전 상태다.

1. **서술** — 무엇을 만족해야 하는지. "빠를 것" 같은 서술은 금지한다.
2. **수용 기준** — 어떻게 통과를 판정하는지. 자동으로 확인할 수 있어야 한다.
3. **출처** — 헌장의 어느 항목 또는 어느 ADR에서 파생됐는지.

**측정하지 않는 요구사항은 요구사항이 아니다.** 수치를 적을 수 없으면
수치를 정할 방법이라도 적는다.

호환 등급이 `L1`인 요구사항의 수용 기준은 **기존 GitHub 클라이언트로 판정한다**
(NFR-COMPAT-02). 우리가 만든 클라이언트로 통과시킨 것은 통과가 아니다.

### 감사 후에도 남은 약점

전수 감사는 **범위의 구멍**을 메운 것이지 요구사항을 성숙시킨 것이 아니다.

- **합의된 것이 거의 없다.** `확정`은 7개뿐이고 나머지는 `초안`·`보류`다.
- **가정 17개 전부 미검증.** 감사로 2개(ASM-16 보안 패치 전달, ASM-17 양방향
  동기화)가 새로 드러났고, 둘 다 없으면 제품 조건이 성립하지 않는다.
- **단계와 요구사항이 연결돼 있지 않다.** Tier는 중요도이지 순서가 아니다.
  지금 상태로는 "단계 2를 마쳤다"를 판정할 수 없다.
- **담당자 지정 0건.**
- 신규 129개는 `근거 항목` 연결이 본문에 직접 들어간 것만 있고,
  기존 항목 41개의 미연결도 그대로다.

## 추적 연결

요구사항 본문에 `근거 항목` 줄이 있다. 그 요구사항이 어느 가정과 제약 위에
서 있는지를 ID로 가리킨다.

```
- **출처**: 헌장 범위 T1, 단계 1
- **서술**: HTTP(S)를 통한 clone / fetch / push를 지원한다.
- **수용 기준**: 표준 git 클라이언트로 왕복 성공.
- **근거 항목**: ASM-07, CON-03, CON-08
```

기존 `출처` 문장은 그대로 두었다. 사람이 읽는 맥락과 기계가 따라가는 참조는
다른 일을 한다.

### 연결 현황

요구사항 185개 중 **144개가 연결됐고 41개는 미연결**이다.

가장 많이 참조되는 것은 `CON-08`(호환 우선, 103건)과 `CON-03`(상류 형태, 73건)이다.
이 둘이 흔들리면 요구사항의 절반 이상이 영향을 받는다.

**미연결 41개는 "근거가 없다"가 아니라 "아직 매핑하지 않았다"이다.**
NFR-SEC 6개, FR-MIG 6개가 가장 크다. 독립적임이 증명된 것이 아니므로
해당 도메인에 착수할 때 다시 본다.

### 참조가 없는 가정·제약

`ASM-13`, `ASM-14`, `ASM-15`, `CON-11`은 어떤 요구사항도 가리키지 않는다.
이것들은 개별 요구사항이 아니라 **헌장 자체를 떠받치기 때문**이다.

특히 `ASM-14`(폐쇄망 수요의 실재)에 참조가 없다는 사실이 그 무게를 오해하게
만들면 안 된다. 이 가정이 무너지면 요구사항 몇 개가 아니라 프로젝트가 무너진다.
