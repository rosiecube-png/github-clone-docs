# 미결 질문 — 인터뷰 백로그

요구사항 도출은 장기전이다. 이 문서는 그 인터뷰가 흩어지지 않게 하는 장치다.

각 질문은 **무엇을 막고 있는지**를 함께 기록한다. 막는 것이 없는 질문은
지금 물을 필요가 없다. 답이 나오면 ADR로 옮기고 여기서는 `해소`로 표시한다.

## 규칙

- 질문 하나가 여러 요구사항을 막을 수 있다. 많이 막는 것부터 묻는다.
- 답이 없어도 진행할 수 있는 작업은 먼저 한다. 질문이 전체를 멈추게 두지 않는다.
- 답을 추측으로 채우지 않는다. 추측이 필요하면 그렇게 표시하고,
  그 위에 되돌릴 수 없는 결정을 쌓지 않는다.
- 해소된 질문은 지우지 않는다. 왜 그렇게 정했는지가 나중에 필요하다.

## 상태

| 상태 | 뜻 |
| --- | --- |
| `대기` | 아직 묻지 않음 |
| `질의중` | 물었고 답을 기다리는 중 |
| `해소` | 답이 ADR로 기록됨 |

## 우선순위 1 — 지금 막고 있는 것

### Q-01 — 재사용 액션을 폐쇄망에서 어떻게 해석할 것인가
- **상태**: 대기
- **막고 있는 것**: FR-CI-05, NFR-COMPAT-05, NFR-OPS-08, FR-CI 도메인 전체의 완성
- **배경**: 워크플로 문법을 호환하면 워크플로는 외부 액션을 참조한다.
  그 해석이 외부 네트워크로 나가면 NFR-OPS-01(에어갭)을 위반한다.
  **문법 호환은 워크플로 호환이 아니다.** 이 질문이 프로젝트에서 가장 큰
  단일 위험이다.
- **필요한 답의 성격**: 미러링 계층을 둘 것인가, 핵심 액션을 내장 구현할 것인가,
  둘 다인가. 반입 절차를 관리자에게 얼마나 맡길 것인가.
- **선행 조사**: 대상 액션들의 재배포 라이선스 확인이 필요하다.
  이건 질문이 아니라 우리가 조사할 일이다.

### Q-02 — 웹 프런트엔드를 어떤 방식으로 만들 것인가
- **상태**: 대기
- **막고 있는 것**: `github-clone-web` 착수 전체, NFR-LIGHT-03, 단계 2
- **배경**: Rust/WASM으로 갈 것인가, 서버사이드 렌더링에 최소한의 JavaScript를
  더할 것인가. 경량성에는 후자가 유리해 보인다. 다만 GitHub 호환 요구가
  들어오면서 판단 근거가 하나 늘었다 — 대형 diff의 줄 단위 코멘트 앵커링
  (FR-PR-03) 같은 상호작용을 재현해야 한다.
- **필요한 답의 성격**: 상호작용 수준과 번들 크기 중 무엇을 우선할 것인가.
- **비고**: 결정 전에 diff 뷰어 프로토타입으로 양쪽을 재 보는 편이 낫다.
  이건 인터뷰가 아니라 실험으로 답할 질문이다.

### Q-03 — CI 작업을 무엇으로 격리할 것인가
- **상태**: 대기
- **막고 있는 것**: FR-CI-12, NFR-SEC-01, 단계 4
- **배경**: 임의의 사용자 코드를 실행하므로 격리 실패는 곧 서버 장악이다.
  그런데 컨테이너 런타임에 의존하면 아키텍처별 실행 이미지 문제가 생겨
  NFR-PORT-01·03과 얽힌다.
- **필요한 답의 성격**: 컨테이너 런타임을 필수 의존성으로 둘 것인가.
  둔다면 NFR-OPS-03(외부 의존성 없음)의 예외로 인정할 것인가.

### Q-04 — 데이터베이스를 내장으로 갈 것인가 외부로 둘 것인가
- **상태**: 대기
- **막고 있는 것**: `github-clone-api` 착수, NFR-LIGHT-01·02, NFR-OPS-03, NFR-SCALE-02
- **배경**: 내장 DB는 단일 노드·경량·에어갭에 유리하고, 외부 DB는 확장과
  운영 도구 생태계에 유리하다. 헌장은 단일 노드를 우선한다고 했으므로
  내장 쪽에 기울지만, 수평 확장 가능성(NFR-SCALE-02)과 상충한다.
- **필요한 답의 성격**: 둘 다 지원할 것인가, 하나로 고정할 것인가.
  둘 다면 추상화 비용을 초기에 치러야 한다.

## 우선순위 2 — 곧 필요한 것

### Q-05 — 호환 기준으로 삼을 상류 API 버전과 추종 주기
- **상태**: 대기
- **막고 있는 것**: NFR-COMPAT-04, NFR-COMPAT-03의 분모 정의
- **배경**: "GitHub과 호환"은 움직이는 표적이다. 기준 시점을 못 박지 않으면
  호환율을 계산할 분모가 없다.
- **필요한 답의 성격**: 특정 시점을 고정할 것인가, 정기적으로 따라갈 것인가.

### Q-06 — 성능 기준 저장소의 규모
- **상태**: 대기
- **막고 있는 것**: NFR-PERF-01(보류 상태), NFR-PERF-02·03의 수치 확정
- **배경**: "대형 저장소"를 정의하지 않으면 성능 요구사항을 측정할 수 없다.
  현재 잠정값은 커밋 10만 개·작업 트리 1GB다.
- **필요한 답의 성격**: 실제로 감당해야 할 최대 저장소의 규모.
  기존 조직의 저장소 통계가 있으면 그게 답이다.

### Q-07 — 인스턴스 규모의 목표 상한
- **상태**: 대기
- **막고 있는 것**: NFR-SCALE-01, NFR-LIGHT-01의 기준 규모
- **배경**: 사용자 20명 규모를 잠정 기준으로 썼다. 목표가 200명이면
  경량성 수치 전체를 다시 잡아야 한다.
- **필요한 답의 성격**: 최소 지원 규모와 목표 상한.

### Q-08 — 패키지 레지스트리의 지원 생태계와 우선순위
- **상태**: 대기
- **막고 있는 것**: FR-PKG-01, NFR-COMPAT-06
- **배경**: 생태계마다 프로토콜이 완전히 다르다. 하나를 구현했다고 나머지가
  따라오지 않으며, 각각이 독립적인 작업량이다.
- **필요한 답의 성격**: 실제로 쓰는 생태계와 그 순서.

## 우선순위 3 — 나중에 정해도 되는 것

### Q-09 — GraphQL 형태 호환(L2)의 구체적 경계
- **상태**: 대기
- **막고 있는 것**: FR-GQL-01·02·06
- **배경**: 어느 깊이까지 맞출지 정하지 않으면 "호환"의 판정이 불가능하다.

### Q-10 — git 객체의 저장 구조
- **상태**: 대기
- **막고 있는 것**: FR-FORK-06(보류 상태), NFR-LIGHT-02의 디스크 산정
- **배경**: 포크 간 객체 공유는 디스크를 크게 아끼지만 격리와 상충한다.
  요구사항에는 격리 우선으로 적어 두었다.

### Q-11 — 지원 리눅스 배포판
- **상태**: 대기
- **막고 있는 것**: NFR-PORT-05의 수용 기준 구체화
- **배경**: 현재 "최소 2개 계열"로만 적혀 있다.

### Q-12 — 라이선스 모델
- **상태**: 대기
- **막고 있는 것**: 배포 시점까지는 막지 않음. 단 Q-01의 액션 재배포 검토와
  간접적으로 얽힌다.

## 우리가 조사해서 답할 것 (인터뷰 대상 아님)

사용자에게 물을 질문이 아니라, 우리가 확인해서 ADR로 기록할 항목이다.

| 항목 | 관련 |
| --- | --- |
| 의존성 후보들이 보장 등급 두 아키텍처에서 크로스 빌드되는가 | ADR-0001, NFR-PORT-04 |
| 순수 Rust git 구현의 성숙도와 성능 | FR-GIT 도메인, NFR-PERF-01 |
| 전문 검색 엔진 후보가 코드 검색 요구를 감당하는가 | FR-SEARCH-03 |
| 재사용 액션들의 재배포 라이선스 | Q-01 |
| 대형 diff 렌더링의 프런트엔드 방식별 실측 | Q-02 |
